# Architecture Review
Generated: 2026-09-01T07:14:12.864Z
Score: 52/100

## Summary
The domain/calculation layer (rateTable, stage, calculateBill, simulate, validate) and the presentational component layer (Card, ScreenScaffold, SummaryHero, etc.) are clean, well-documented, and consistently used. However, the data-access layer is duplicated wholesale — three entities (appliances, profile, report-unlocks) each have two parallel, independently-maintained implementations (a hook version and a plain-function 'lib' version) — and several type definitions conflict outright between files. Combined with dead code left over from a contract/scaffolding step and inline reimplementation of logic that already exists in domain/lib modules, the codebase shows signs of AI-scaffolded duplication that was never consolidated.

## Issues
### Critical
- [duplication] Three complete, parallel implementations of localStorage-backed CRUD logic exist for the same entities: hook-based (returns state + callbacks) and plain-function 'lib' versions, using identical keys and near-identical logic. Only one side of each pair appears to actually be imported by pages/components (the hooks), leaving the 'lib' versions as unreferenced duplicates that will silently drift out of sync (e.g. lib/appliances.ts's addAppliance doesn't set `reason` on write failure while the hook version implicitly does via writeJSON's result). — Files: src/hooks/useAppliances.ts, src/lib/appliances.ts, src/hooks/useProfile.ts, src/lib/profile.ts, src/hooks/useReportUnlock.ts, src/lib/unlocks.ts / Fix: Pick one data-access pattern (recommend: hooks as thin wrappers over the plain lib functions, calling getAppliances/addAppliance/etc. from lib/*.ts instead of reimplementing loadAppliances/loadProfile/loadUnlocks). Delete the redundant implementation and its duplicated KEY/TTL/MAX constants.
- [naming] `AppFlags` is defined twice with incompatible field types: `src/lib/types.ts` declares `disclaimerSeenAt: string | null` while `src/types/domain.ts` declares `disclaimerSeenAt: number | null`. Any code importing the wrong one will silently pass/accept the wrong type (e.g. a Date.now() number written where a string is expected), which TypeScript won't catch across module boundaries since both are named identically but never unified. — Files: src/lib/types.ts, src/types/domain.ts / Fix: Delete one definition and import the other everywhere. Settle on a single source of truth for storage-related types (types/domain.ts, since it's the more actively used location) and re-export from lib/types.ts if backward compatibility is needed.
- [naming] `BillBreakdown`/`StageBreakdown(Row)` are defined twice with different shapes: `src/lib/types.ts` version omits `climateCharge`/`fuelCharge` fields that `src/types/domain.ts` version includes, yet `src/domain/calculateBill.ts` (which actually computes and returns both of those fields) types its return value against the `lib/types.ts` version. This mismatch means the real returned object has more fields than its declared type promises, and any consumer importing from `types/domain.ts` instead gets an incompatible structural type for the same runtime data. — Files: src/lib/types.ts, src/types/domain.ts, src/domain/calculateBill.ts / Fix: Consolidate to one BillBreakdown/StageBreakdown definition (matching the actual calculateBill return shape, i.e. the types/domain.ts version) and have calculateBill.ts import from there.

### Suggestions
- [duplication] A local `won(value)` currency formatter (`formatNumber(value) + '원'`) is redefined independently in History.tsx, Result.tsx, Report.tsx, and Simulate.tsx, even though `src/lib/utils.ts` already exports a `formatCurrency` function intended for this purpose (which itself appears unused/dead). — Files: src/pages/History.tsx, src/pages/Result.tsx, src/pages/Report.tsx, src/pages/Simulate.tsx, src/lib/utils.ts / Fix: Either use formatCurrency from lib/utils.ts everywhere and delete the four local `won()` copies, or delete formatCurrency and keep a single shared `won()` helper in lib/utils.ts.
- [structure] `src/types/storage.ts` exports a `StorageKey` union type ('es:records' | 'es:profile' | ...) but every module that touches localStorage (lib/records.ts, lib/profile.ts, lib/appliances.ts, lib/unlocks.ts, hooks/*, pages/History.tsx, pages/Region.tsx, pages/Settings.tsx) hardcodes its own local `KEY = "es:..."` string literal instead of importing/using this type, so there is no actual compile-time protection against key typos or drift. — Files: src/types/storage.ts, src/lib/records.ts, src/pages/Settings.tsx / Fix: Export the key string constants themselves (not just the type) from types/storage.ts and have every consumer import them, eliminating hardcoded duplicate string literals.
- [structure] Data-access responsibilities are split unclearly between `src/hooks/` and `src/lib/` for the same three entities (appliances, profile, report-unlocks), with no naming or folder convention indicating which is canonical. This invites the exact duplication described above and makes it unclear where new persistence logic should go. — Files: src/hooks/useAppliances.ts, src/lib/appliances.ts, src/hooks/useProfile.ts, src/lib/profile.ts / Fix: Adopt one convention: lib/*.ts holds framework-agnostic read/write functions, hooks/*.ts are thin React-state wrappers around them (never reimplementing the load/save logic directly).
